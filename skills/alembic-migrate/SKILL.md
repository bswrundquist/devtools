# Alembic Migrations

Manage database schema migrations with Alembic + SQLAlchemy 2.0.

## Everyday commands

| Task | Command |
|---|---|
| Autogenerated migration | `uv run alembic revision --autogenerate -m "add user table"` |
| Empty migration (data fixes) | `uv run alembic revision -m "backfill emails"` |
| Apply all | `uv run alembic upgrade head` |
| Apply one step | `uv run alembic upgrade +1` |
| Roll back one step | `uv run alembic downgrade -1` |
| Current DB state | `uv run alembic current` |
| History / heads | `uv run alembic history --verbose` / `uv run alembic heads` |
| Merge divergent heads | `uv run alembic merge heads -m "merge branches"` |
| Render SQL for DBA review | `uv run alembic upgrade head --sql > migrate.sql` |

## What autogenerate misses — always review the diff

`--autogenerate` compares model metadata to the live DB, but it does NOT detect:

| Blind spot | Consequence |
|---|---|
| Column/table renames | Emitted as drop + add — silent data loss if applied as-is |
| Server defaults | Ignored unless `compare_server_default=True` |
| Enum value changes (Postgres) | No `ALTER TYPE ... ADD VALUE` emitted — write by hand |
| CHECK constraints | Usually not detected at all |
| Type changes | Only detected with `compare_type=True` |

Enable the comparators in `env.py`:

```python
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    compare_type=True,
    compare_server_default=True,
)
```

Fix a rename manually — replace the generated drop+add:

```python
def upgrade() -> None:
    op.alter_column("users", "fullname", new_column_name="full_name")

def downgrade() -> None:
    op.alter_column("users", "full_name", new_column_name="fullname")
```

## Non-nullable column on an existing table

Never add `nullable=False` in one shot on a populated table. Three phases: add nullable → backfill → constrain.

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("tier", sa.String(20), nullable=True))
    op.execute("UPDATE users SET tier = 'free' WHERE tier IS NULL")
    op.alter_column("users", "tier", nullable=False)

def downgrade() -> None:
    op.drop_column("users", "tier")
```

For large tables, split the phases across separate migrations/deploys so the backfill can run batched, outside a long lock.

## Data migrations

Use `op.get_bind()` with lightweight core table objects. Never import ORM models — they describe the schema as of current code, not as of this revision, and will break old migrations later.

```python
import sqlalchemy as sa
from alembic import op

def upgrade() -> None:
    conn = op.get_bind()
    users = sa.table(
        "users",
        sa.column("id", sa.Integer),
        sa.column("email", sa.String),
    )
    for user_id, email in conn.execute(sa.select(users.c.id, users.c.email)):
        conn.execute(
            users.update().where(users.c.id == user_id).values(email=email.lower())
        )
```

Prefer a single set-based `UPDATE` over row loops when the transformation is expressible in SQL.

## Multiple heads

Two branches each adding a migration off the same parent produces two heads; `upgrade head` refuses to run.

```bash
uv run alembic heads                              # shows 2 heads
uv run alembic merge heads -m "merge feature branches"
uv run alembic upgrade head
```

Prevent it from reaching main — fail CI on divergence:

```python
from alembic.config import Config
from alembic.script import ScriptDirectory

def test_single_head() -> None:
    script = ScriptDirectory.from_config(Config("alembic.ini"))
    assert len(script.get_heads()) == 1, "run: alembic merge heads"
```

## naming_convention — set before the first migration

Deterministic constraint names let autogenerate drop/alter them later (SQLite and Postgres auto-names differ and are not portable).

```python
from sqlalchemy import MetaData
from sqlalchemy.orm import DeclarativeBase

convention = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}

class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=convention)
```

## Offline mode

`alembic upgrade head --sql` renders the SQL without touching a database — for DBA review or environments where the app has no DDL rights. Data migrations that read rows can't run offline; guard with `context.is_offline_mode()` or keep them pure `op.execute()` SQL.

## Rules

- Always review autogenerated migrations before applying — autogenerate produces a draft, not a result.
- Never edit a migration already applied to production (or any shared environment). Write a new migration on top instead.
- Non-nullable columns on existing tables: add nullable → backfill → constrain. Never in one step on a populated table.
- Every `upgrade()` gets a real `downgrade()`. If truly irreversible (dropped data), raise `NotImplementedError` with a comment — never a silent `pass`.
- Data migrations use `op.get_bind()` + `sa.table()`/`sa.column()` — never ORM models.
- One logical change per migration: easier review, safer rollback.
- Check `alembic heads` in CI; fail on more than one head.
- Set `naming_convention` before the first migration — retrofitting requires rewriting constraints.
- Descriptive `-m` messages ("add index on orders.user_id"), never "update" or "fix".
- Use `--sql` offline mode whenever DDL must be reviewed before hitting production.
